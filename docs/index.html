odm

A CLI download manager that takes one connection budget and splits it sensibly — across files, across engines, across mirrors. Inspired by aria2c. Written in Go.

1.0

quickstart

three invocations cover everything.

# one file, 16 parallel connections
odm -c 16 https://files.test.xyz/file.tar.gz

# a batch: -c controls how many files run at once, 1 connection each
odm -c 16 url1 url2 url3 …

# or 4 connections per file → 4 files at a time, the rest queue
odm -c 16 -sf 4 url1 url2 url3 …

Large lists go in a file — one URL per line, # comments allowed:

odm -i file-list.txt

Every run probes each URL first (HEAD → ranged GET → single-stream fallback), shows the plan, and asks once before moving bytes. -y skips the prompt; --dry-run stops after the plan.

2.0

the connection balancer

-c is a budget, not a guess.

You set one number — the total parallel-connection budget. The balancer decides what it means from the shape of the job:

allocation modes
modewhen-c controlsper file
Aone URLwhole budget → the filemin(-c, 32)
Bmany URLs, no -sffiles in parallel1
Cmany URLs + -sf Nfloor(-c / N) files at onceN + remainder

Files whose server refuses HTTP range requests get exactly one connection, and the freed budget is redistributed to the rest in the same pass. Above the soft ceiling of 32, odm warns and proceeds.

Within a file, work is a queue of fixed-size chunks (default 4 MiB). Workers — one per allocated connection — pull the next chunk the moment they finish the last, so a slow connection processes fewer chunks instead of holding the file hostage. Static equal-split tools call this the straggler problem; here it simply doesn’t happen.

3.0

engine profiles

four engines. one flag.

--profile NAME changes how bytes move. The default is odm; smart picks per file after probing.

odm

Fixed chunks in a work-stealing queue over N real HTTP/1.1 connections. The default, and the point of the tool — multi-connection aggregation.

aria2c

Static equal split into --split segments, multiplexed as HTTP/2 streams over one connection. Mirrors aria2c’s -s/-x model on HTTPS servers.

both

A 50/50 split: first half on the odm engine, second half on the aria2c engine — both engines working the same file at once. Files under 4 MiB degrade to plain odm.

smart

Probes range support, size, and h2 readiness, then picks per file: small or non-rangeable → odm; ≥ 256 MiB with ≥ 6 conns → both; otherwise → aria2c. Set it and forget it.

4.0

resume & integrity

interrupted is not corrupted.

Each download writes a .odm control file recording finished chunks. Re-run the same command and only the missing ranges are fetched. On resume, the stored ETag rides along as If-Range: if the remote file changed since the interruption, odm detects it and restarts cleanly instead of stitching old bytes to new ones.

Completed chunks carry SHA-256 digests in the control file, verified against disk before a resume continues. Verification against the source comes three ways: --checksum sha256:<hex>, --checksum-url (sha256sum-style sidecar), or embedded in a Metalink4 document via -i file.meta4.

Mirrors (--mirror URL, repeatable) join the per-chunk rotation — a throttling source serves fewer chunks while the rest keep full speed. Each mirror’s responses are validated independently, so a misbehaving one fails its own chunks, not your file.

When a server answers 429, the global rate halves on its own so every connection eases off together, then restores your configured cap after a quiet period.

5.0

rpc daemon

drive it from anywhere.

odm --rpc serves JSON-RPC 2.0 on /rpc and WebSocket events on /ws — the same relationship aria2c has with AriaNg. Default bind 127.0.0.1; pair --rpc-listen-all with --rpc-secret.

# start the daemon
odm --rpc --rpc-secret hunter2 -d ~/Downloads &

# add a download — token:<secret> is the first param
curl -s -X POST http://127.0.0.1:6900/rpc \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"odm.addUri",
       "params":["token:hunter2","https://files.test.xyz/x.tar.gz"],"id":1}'

Five events stream over /ws: start, progress (≈250 ms throttle), complete, error, pause — each carrying the same field set as tellStatus.

odm.addUri / addBatchqueue one or many URLs
odm.pause · unpause · removesteer running tasks (also *All variants)
odm.tellStatus / Active / Waiting / Stoppedinspect tasks by state
odm.changeOptionrate limits + connections, mid-flight
odm.getGlobalStat · getVersioncounts and capabilities
odm.shutdownwind the daemon down
